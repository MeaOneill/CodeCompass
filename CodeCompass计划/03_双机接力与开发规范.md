# 双机接力与可追溯开发

## 1. 可行方式

可以由两位成员分别在各自电脑、各自账号下运行Agent，共用同一个Git远程仓库；A保存代码与交接后，B拉取并继续。工程上不需要迁移完整聊天记录：**代码版本+配置+运行记录+交接文件**才是项目上下文。无需等待A额度彻底耗尽再保存。

两台电脑或两个账号不等于自动共享文件、模型记忆和任务状态；也不能承诺产能严格翻倍。官方说明本地与云端任务共享相应计划用量、还可能有周限额；用量随任务和模型而变化。各账号以自己的额度界面为准。[官方定价与用量说明](https://learn.chatgpt.com/docs/pricing)

Codex worktree用于隔离Git工作副本，不会把另一台机器文件自动同步；跨机仍使用远程Git或显式交接包。[官方worktree说明](https://learn.chatgpt.com/docs/environments/git-worktrees)

这是协作工程方案，不是账号额度转移功能。各自保持登录和凭据，项目API凭据也通过本地环境配置，不能提交到仓库。应用运行所需服务费用单独测算。本次只生成规范，尚未配置两台电脑、远程仓库或自动切换。

## 2. 两种日常模式

**优先：接力。** 当前Owner完成一个45—60分钟或更小子任务，写日志并push。新Owner拉取同一交接分支，从最后通过验收的检查点继续。新Owner确认接管后，旧Owner不再改该任务。

**必要时并行：** A只改graph/learner/planner；B只改app/retrieval/issues/文档与指定评测脚本。`contracts`、依赖锁文件、评测协议与共享schema只允许指定集成负责人改。需要跨目录变化先登记接口变更，不同时重构。

一天安排两条任务线不要求两个Agent全天在线。额度不足时先保存一个线的状态再接另一线；依赖未满足的工作等候，另一方做独立任务。

## 3. 仓库规则

- `main`只放验收过的版本；开发使用`task/A-Dxx-topic`、`task/B-Dxx-topic`。
- 每个任务在TASK_BOARD记录owner、machine、branch、base_commit、状态和心跳时间。无原子锁服务时由队长确认认领；单靠同时编辑Markdown无法防止两人抢占。
- 状态：TODO → CLAIMED → IN_PROGRESS → READY_FOR_REVIEW → DONE；失败BLOCKED；中断PAUSED。额度用完不是DONE。
- 代码、配置、数据schema、小型许可允许的样例入Git；个人记录、密钥、运行中的SQLite、虚拟环境、大模型权重不入Git。大结果上传双方可访问存储，交接单记录路径/访问方式/SHA256；不要写临时本机路径当共享地址。
- 开发原始记录和官方评审材料分开导出；原始署名不篡改，评审导出材料按规则去学校/教师信息。
- 不强推覆盖、不用reset --hard清理未交接修改、不复制覆盖另一台电脑整个目录。

## 4. 标准交接操作

首次具体步骤见05_Git远程仓库创建与日常维护.md。队长先网页创建空私有远程并邀请成员；已有项目的第一台电脑检查后初始化、首次上传，第二台再clone同一远程并演练反向push。记录实际origin、权限和同步SHA。本次文档更新尚未执行上述操作。

交出方：
1. 停在小任务边界，查看`git status`和diff；核对待提交文件无凭据或个人数据。
2. 写会话日志，更新STATUS、HANDOFF和任务状态，标明代码是否可运行。测试失败也要写清楚。
3. 显式`git add`本次文件，提交并push当前交接分支。交接未完功能用`wip:`描述，不合入main。
4. 记录远程实际commit SHA并通知另一位成员。HANDOFF中可写“当前交接提交的父提交为X；准确交接SHA以任务通知和git rev-parse HEAD为准”，避免文档自引用哈希悖论。

接收方示例（分支名以交接单为准）：
```powershell
git status
git fetch origin
git switch task/A-D01-contracts
git pull --ff-only
git rev-parse HEAD
```
首次未有本地分支时用`git switch --track origin/实际分支`。有未提交修改先保存自己的分支检查点，不能直接覆盖。上述是示例流程，不代表分支已经存在。

接收方随后：核对SHA、依赖锁定和输入数据hash → 阅读交接 → 执行最小smoke命令 → 记录已接管 → 继续下一个明确子步骤。若检查不通过，先记录环境问题，不重新设计整个项目。

任务完成后由另一位成员或另一个会话复核diff与验收命令，集成负责人合入main；自审需明确标“自审”，不能伪称独立复核。

## 5. 意外断额恢复

每45—60分钟保存一次检查点和handoff；复杂实验按run_id持续写入JSONL并原子保存结果文件。不能等额度清零才让Agent总结。

若Agent已无法响应：由人类运行`git status`并保存diff、当前分支和HEAD；用编辑器写3行“已完成/正在做/待做”；确认无秘密信息后提交显式文件并push。若不熟悉Git，复制源码与日志形成时间戳zip（排除.env、用户数据、.venv），附文件哈希清单。B在新目录恢复，人工比对，不覆盖既有副本。

运行中的实验可以继续由普通Python进程执行，不依赖聊天持续在线。交接记录PID、命令、日志文件和输出目录；B先检查是否已有结果，不能重复启动相同run_id。需要跨机重跑时使用新run_id并保留中断状态。

## 6. 可直接发给接力Agent的话

> 你正在接手CodeCompass，不是从头设计。先读CodeCompass计划/tracking/STATUS.md、HANDOFF.md、TASK_BOARD.md、最近一次会话日志、当天任务卡和实验协议。核对git status、当前分支/HEAD与交接SHA，确认数据hash和依赖。先报告接管的任务ID、最后通过的验收及下一步，再执行交接中的第一个未完成动作。不要重复已完成工作；不要改冻结指标、数据或算法主线。每个检查点更新日志；结束前提交可恢复工作并准备下一份交接。团队确认origin并进入本计划执行后，每轮例行任务分支commit/push按维护要求执行；公开仓库、第三方提交和比赛正式提交不在例行维护范围。若发现矛盾，保留文件、记录冲突并先做不受影响的任务。

## 7. 日志最低要求

每次会话一个独立文件`tracking/sessions/YYYYMMDD-HHMM_actor_machine_task.md`，减少多人争写。包括人类负责人、Agent提供方/模型（未知填unknown）、机器、任务、base/head、起止时间、修改、命令、实际输出摘要、原始路径、风险、下一步。日志署名与人类审核分开。

每个实验记录run_id、code_commit、data/config/prompt_hash、模型标识、seed、输入版本、开始结束、退出状态、原始结果路径、环境、费用、是否模拟。记录失败实验；图表登记源run_id与脚本版本。

每个重大决定写ADR：原因→候选方案→开发证据→决定→影响→复核条件。没跑实验的决定写“基于工程判断”，不能写“验证证明”。

一个任务DONE的条件：产物存在、实际运行验收通过、失败和限制披露、日志更新、下一位可恢复；“代码写好了”不等于完成。

## 8 每日Git维护与里程碑

本轮Git开始检查：若尚未建仓，先执行D01首次配置，不盲目运行后续Git命令；已建仓时先看git status -sb、当前分支和Owner，再git fetch origin。新任务从已验收main或明确登记的依赖版本创建任务分支，接力原任务继续同一分支并核对上一棒SHA。有未提交修改先保存归属明确的检查点，不直接pull覆盖；远程未就绪如实记同步受阻。

本轮Git收尾验收：先完成必要验证和状态/日志/贡献/交接/图表索引，再检查diff，显式git add本轮文件，commit并push当前任务分支，核对remote SHA等于HEAD。未完成保存wip并记PAUSED/BLOCKED，不合入main；完成先记READY_FOR_REVIEW，实际复核后由指定集成负责人合入main。回复给出分支、base/HEAD/remote SHA、同步状态与下一步。没有新文件变化记录无新提交；push失败不写双机同步完成。

D01首次建立与双机验证；D06协议冻结标签；D14候选标签；D15按标签异机复现；D16实际提交后最终标签与材料hash。标签只在里程碑通过后创建，不强推覆盖。小型代码/配置/匿名结果/图表索引入库，大原始数据/视频另存可访问路径和hash。具体任务已写进每天安排与两份成员手册。
